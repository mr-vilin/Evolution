# MySQL 字符串排序规则统一

迁移 `0022_mysql_general_ci` 将 `0021_tencent_db_conventions` 中的 27 张表、68 个 `utf8mb4_bin` 字符串列改为 `utf8mb4_general_ci`。保留 UTF-8 编码、字段定义、中文备注、主键、索引和现存外键。等值匹配、唯一约束、分组和排序随目标规则生效，迁移后应从第一页重新获取跨迁移前后的分页游标。

## 执行前

1. 核对目标环境、MySQL 8.4、InnoDB、库及表的 `utf8mb4_general_ci` 默认值、应用会话和实际迁移版本。使用 `schema_snapshot` 保存结构基线。
2. 对已有数据的实例，停止应用、MCP、worker 和其他写入方。保留一致性备份并在隔离实例恢复，使用同一候选制品演练升级与恢复。迁移在首条 DDL 前按完整唯一索引和外键检查目标规则下的冲突，只报告表和约束名。
3. 本地全新安装可用独立的空 MySQL 卷。先核对原卷，创建新卷，用本机 `.env` 的 `MYSQL_VOLUME_NAME` 选择它，保留原卷和镜像。执行前核对实际挂载路径与卷名。

## 执行与验证

使用候选制品的 `migrate` 服务执行 `alembic upgrade head`。MySQL 会复制受影响表，应留足磁盘空间。迁移会话暂时关闭外键检查，逐表修改已完成数据检查的关联列，并恢复原会话设置。发布流使用 Alembic 在线迁移，离线 SQL 用于审阅。

升级完成后，用应用连接运行 `app.persistence.schema_check` 并核对迁移版本、非 `general_ci` 字符串列数量、索引及外键。升级已有数据时再比对业务行数或摘要。通过后启动同制品 app 和 MCP，并执行 `deploy/release.py verify`。

## 失败恢复

MySQL DDL 分表提交。中断后保持停写，检查版本、列排序规则和外键状态。可以在处理失败原因后使用同一制品重跑，迁移会跳过已转换的列。已有数据实例可按已演练的备份恢复并使用旧镜像。

本地换卷时，停止 app、MCP 与 MySQL，恢复原 `MYSQL_VOLUME_NAME` 配置和发布覆盖文件，重建 MySQL 容器以挂回原卷，启动原镜像并重新检查健康与迁移版本。保留新旧卷用于核对。

降级恢复 68 列原规则，执行前同样检查目标规则下的外键。迁移后若有仅凭大小写不敏感比较才能成立的外键关系，先处理这些引用或恢复迁移前备份。
