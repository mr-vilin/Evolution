## Problem Statement

管理员需要在完整企业组织中定位部门、查看当前成员、选择准确的部门范围并维护门店属性。当前页面先读完部门及人员，树默认展开，人员表格的 20 条是客户端分页；数据较多时无法按展开和滚动逐步读取。部门搜索依赖浏览器数据且包含本轮不需要的 ID 搜索，人员缺少姓名、手机号和 USER_ID 搜索及真实账号状态筛选，同父级展示顺序无法持久保存。

现有独立勾选不能表达管理员要求的四步范围切换，也不能在异步树中证明未加载下级已被完整纳入。失效部门未明确标记，可能混入批量目标。组织页批量设置目前要求预览后确认，且最多 500 个部门，无法满足整批选择有效部门、只显示准确选中数量并直接保存的要求。数据发生变化时，管理员还需要保留草稿，并明确核对新的实际目标。

## Solution

组织架构页采用受控组织树，首次只显示【组织】及收起的一级部门，继续展开时读取直接下级。同父级部门可拖拽排序并保存到数据库，供管理员共享。部门名称在完整已同步数据中按任意片段搜索，结果保留祖先路径；默认仅显示有效部门，可切换查看有状态标记的失效部门。

选中具体部门后，人员默认按直属成员查询，包含有效兼职归属，可切换为本部门及全部下级的去重成员。人员首批 20 人，滚动每批再读 20 人；姓名片段、完整手机号、精确 USER_ID 与真实账号状态条件共同决定列表及去重总人数。缺失或不可读信息明确为未知，查询不扩大为历史离职、退出人员名单。

部门勾选与浏览、展开分别受控，父部门按“均未选 → 仅本部门 → 本部门及全部下级 → 仅下级 → 均未选”循环，并保留手动调整后的部分下级。选中数量覆盖未加载的有效部门。组织页批量入口支持超过 500 个部门，结构化编辑后直接保存，服务端仍完整校验并整批提交或回滚；发生世代或版本冲突时保留草稿，重新核对范围后由用户再次保存。

## User Stories

1. 作为组织管理员，我希望首次进入只看到【组织】和一级部门，以便在大型组织中逐层浏览。
2. 作为组织管理员，我希望一级部门初始收起，以便自行决定查看哪些分支。
3. 作为组织管理员，我希望展开时只读取该节点直接下级，以便不必等待全企业部门加载完成。
4. 作为组织管理员，我希望下级加载失败时保留现有内容并能重试，以便继续浏览。
5. 作为组织管理员，我希望分别控制节点点选、展开和范围勾选，以便查看人员时不误改批量目标。
6. 作为组织管理员，我希望在未选具体部门和点选【组织】时看到选择部门提示，以便避免误查全企业人员。
7. 作为组织管理员，我希望通过拖拽调整同父级部门顺序，以便按日常工作习惯浏览。
8. 作为组织管理员，我希望刷新后及其他管理员进入时仍能看到保存的顺序，以便共享一致的展示结果。
9. 作为组织管理员，我希望日常飞书同步保留本地顺序，以便已有整理不被覆盖。
10. 作为组织管理员，我希望新增及移入的部门追加到新组末尾，同 ID 同父级恢复时保留原顺序，以便顺序变化可理解。
11. 作为组织管理员，我希望拖拽不会改变部门隶属或写回飞书，以便展示调整不变成组织事实变更。
12. 作为组织管理员，我希望搜索局部结果时停用拖拽，以便不完整视图不会覆盖整组顺序。
13. 作为组织管理员，我希望按部门名称任意片段搜索完整已同步组织，以便找到尚未展开或加载的部门。
14. 作为组织管理员，我希望部门搜索结果保留祖先路径，以便理解命中部门的位置。
15. 作为组织管理员，我希望清空搜索恢复搜索前的展开状态，以便继续原来的浏览任务。
16. 作为组织管理员，我希望搜索和显示条件变化不会悄悄清空已有勾选，以便保留已确认的批量范围。
17. 作为组织管理员，我希望默认只浏览有效部门，以便聚焦当前组织。
18. 作为组织管理员，我希望可切换显示有明确失效标记的部门，以便查询既有资料。
19. 作为组织管理员，我希望失效部门始终排除在批量选择和门店设置之外，以便避免无效目标使整批操作失败。
20. 作为组织管理员，我希望人员默认显示当前部门直属成员并包含有效兼职归属，以便准确了解当前归属。
21. 作为组织管理员，我希望切换为本部门及所有层级下级的全部成员，以便查看完整分支人员。
22. 作为组织管理员，我希望跨多个部门归属的同一人员在列表和总人数中只出现一次，以便不重复统计。
23. 作为组织管理员，我希望只查询当前有效部门归属的成员，以便不将历史离职、退出名单混入当前列表。
24. 作为组织管理员，我希望通过一个入口搜索姓名片段、完整手机号或精确 USER_ID，以便快速定位当前范围内的人员。
25. 作为组织管理员，我希望手机号只在去除首尾空白后精确匹配，且不猜测国家区号，以便搜索含义明确。
26. 作为组织管理员，我希望 USER_ID 对应飞书用户标识，以便不与工号或 open_id 混淆。
27. 作为组织管理员，我希望搜索与成员范围、账号状态条件共同生效，以便准确缩小当前部门内的结果。
28. 作为组织管理员，我希望可单选全部、已激活、未激活、已暂停、未加入或状态未知，以便按真实账号事实筛选。
29. 作为组织管理员，我希望多个账号状态事实可同时保留，以便不被虚构的互斥状态误导。
30. 作为组织管理员，我希望手机号及账号标志的缺失、不可读与合法空值能被区分，以便不会把未知信息当成确定事实。
31. 作为组织管理员，我希望首批人员只读取 20 人，向下滚动再读取下一批 20 人，以便尽早开始查看。
32. 作为组织管理员，我希望分别看到筛选后的去重总人数和已加载人数，以便了解查询规模及加载进度。
33. 作为组织管理员，我希望部门或条件变化后重置人员列表、游标和滚动位置，以便不混入旧条件结果。
34. 作为组织管理员，我希望人员加载中、失败可重试和没有更多均有反馈，以便知道下一步如何操作。
35. 作为组织管理员，我希望点击普通父部门勾选时按指定四步循环切换，以便表达仅本部门、包含下级和仅下级。
36. 作为组织管理员，我希望“全部下级”覆盖所有层级及未展开、未加载、被搜索隐藏的有效部门，以便批量范围完整。
37. 作为组织管理员，我希望手动取消或选择部分下级后保留实际集合，并看到“部分下级”，以便精确调整范围。
38. 作为组织管理员，我希望父部门与部分下级已选时，下次点击只取消父部门，再次点击才清空分支，以便保留逐步切换的含义。
39. 作为组织管理员，我希望下级选择全部清空后范围自然回到仅本部门或未选，以便标记符合实际集合。
40. 作为组织管理员，我希望操作一个分支不会清空其他分支，以便组合多个独立目标。
41. 作为组织管理员，我希望【组织】仅全选或清空其下全部有效部门，部分选中时点击清空，以便管理企业范围且不把虚拟根作为目标。
42. 作为组织管理员，我希望没有下级的叶节点只在选中与清空之间切换，以便操作符合节点能力。
43. 作为组织管理员，我希望范围标记区分未选、仅本部门、本部门及下级、仅下级，并另标全部或部分，以便理解勾选结果。
44. 作为组织管理员，我希望勾选只确定目标，保存才修改属性，且门店属性不自动继承，以便避免意外写入。
45. 作为组织管理员，我希望常驻看到去重后的“已选 N 个部门”，且排除虚拟根与失效部门，以便核对实际目标数量。
46. 作为组织管理员，我希望范围解析中看到正在计算，数量确定且非零后才能开始批量设置，以便不会把浏览器节点数误认成真实数量。
47. 作为组织管理员，我希望可一次设置实际选中的全部有效部门，包括超过 500 个部门的范围，以便完成整批维护。
48. 作为组织管理员，我希望使用有中文标签及字段校验的结构化表单编辑门店属性，以便不必编写 JSON。
49. 作为组织管理员，我希望组织页批量编辑后点击保存即提交，不再预览影响或二次确认，以便按已确认流程完成操作。
50. 作为组织管理员，我希望提交中避免重复触发，成功后看到实际保存结果，以便判断操作是否完成。
51. 作为组织管理员，我希望字段、门店编码或权限校验失败时整批不写入且保留输入，以便修正后再保存。
52. 作为组织管理员，我希望批量属性、审计和人员门店投影同时成功或同时回滚，以便系统记录一致。
53. 作为组织管理员，我希望数据变化或初始化切换后识别世代与版本冲突，以便旧范围不会被错误写入。
54. 作为组织管理员，我希望冲突后保留草稿、重新核对目标与数量，并由我再次保存，以便新部门不会静默加入旧批次。
55. 作为组织管理员，我希望多人同时排序时检测冲突，以便我的修改不被静默覆盖。
56. 作为组织管理员，我希望组织页单部门编辑、门店页单条编辑及 Agent/MCP 保持各自既有协议，以便本次批量流程调整不连带改变其他入口。

## Implementation Decisions

- **确认状态**：Q1 至 Q11 已有业务答复；下列工程细化来自输入文档最终实施基线。Q12 尚待确认共同理解及开始实现，本规格与 `ready-for-agent` 标签均不替代该确认。
- **既定架构**：沿用 React、TypeScript、Ant Design Pro v6 工程约定、Ant Design 6.6.4、Umi Max、FastAPI、SQLAlchemy、官方飞书 SDK 及 MySQL 8.4；保留当前代码分离、合并部署拓扑和管理员门禁。实施时按实际依赖与官方资料核对 Tree API。
- **组织页状态**：树的展开、节点点选、实际部门选择范围分别受控。虚拟根是【组织】，一级部门为其直接下级。首次显示根及一级部门，一级部门保持收起；未选具体部门及点选根节点均不请求全企业人员。
- **按需树读取**：组织读取服务补充直接下级读取所需的子节点存在信息；单次展开只加载该节点直接下级，保留分页能力，不递归预取整棵树。当前世代及版本内可以复用已加载结果；失败保留节点和已有内容并支持重试。
- **本地顺序**：部门增加本地非负整数 `sort_order`，只表达同父级展示顺序，所有管理员共享。既有未排序部门按稳定 ID 初始化；新增及跨父部门移入的部门追加到新组末尾，同 ID 同父级恢复保留原顺序。普通同步保留本地顺序，初始化重来按既有清理边界处理。
- **排序写入**：仅接受同父级间隙排序，不变更父部门、不回写飞书。搜索期间停用拖拽；可见结果不完整时不得以局部列表替换完整同组顺序。同组并发修改采用版本校验，冲突不静默覆盖。具体排序请求形状在实现中确定，服务端核实父级及实际目标。
- **部门搜索与有效性**：部门搜索仅按名称任意片段匹配，由后端检索完整已同步数据，并遵守“显示失效部门”条件，返回命中节点及祖先路径。清空搜索恢复此前展开状态；搜索条件变化不悄悄清空批量选择。默认仅显示有效部门；失效部门明确标记，仅供查询，不参加批量选择和保存。
- **人员搜索**：一个关键词入口采用“姓名片段或手机号精确值或 USER_ID 精确值”匹配，并与当前部门、成员范围、账号状态条件取交集。手机号去首尾空白后比对，不支持后几位匹配、不自动猜国家区号；USER_ID 指飞书 `user_id`，不扩展到工号或 open_id。
- **成员范围**：仅查询具有当前有效部门归属的人员。默认直属，包含兼职有效关系；全部成员包含本部门及所有层级下级，按人员稳定标识去重。查看失效部门或选择账号状态“全部”均不恢复历史关系，也不推断离职前部门。
- **人员分页与计数**：停止组织页人员全量读取后客户端分页，首批与滚动续载均为 20 人。服务端提供当前完整条件下的去重匹配总数、下一游标及世代/版本元信息，人数与当前加载条数分别展示。查询条件变化重置列表、游标和滚动；迟到的旧响应不得追加到新结果。无下一游标即停止续载，失败可重试。
- **账号事实**：保存飞书暂停、离职、激活、主动退出、未加入五个可缺省布尔标志，保留现有系统记录有效/失效语义。下拉单选“全部”（默认）、“已激活”、“未激活”、“已暂停”、“未加入”、“状态未知”；分别按相关原始标志匹配，未激活必须为激活标志明确为 false。不同状态条件可命中同一人员，不强制互斥，也不为展示虚构状态优先级。本页所需账号标志缺省或不可读时明确标未知，不填充为 false。
- **手机号与可读性**：补齐手机号及账号标志的采集、规范化、存储、读取响应和前端领域类型，复用初始化逐字段可读性说明，区分未采集、不可读和合法空值。缺失手机号不等同于已证明为空或确定无权限；SDK 存在 `mobile`、`mobile_visible` 不构成实际应用有权限的证明。
- **完整选择范围**：应用维护实际选中部门集合及分支下级完整性，服务端参与完整范围解析与计数，不能只依赖树缓存。普通父部门循环为“均未选 → 仅本部门 → 本部门及全部有效下级 → 仅有效下级 → 均未选”；操作一个分支不修改无关分支。
- **部分下级**：父部门是否选中与下级是否全选分开表达；手动调整下级保留实际集合并标“部分下级”。父已选且部分下级已选时，下一次点击仅取消父部门，再点清空该分支；不补回已取消下级。无下级选中时，自然回到仅本部门或未选。原生复选框外观不独自承担四态语义。
- **根与叶节点**：【组织】只全选或清空全部有效部门，自身不进入批次；部分已选时点击清空。没有下级的叶节点仅选中/清空。全部下级包含所有层级及未展开、未加载、被搜索隐藏的有效部门。
- **选中计数与编辑门槛**：常驻显示去重后的“已选 N 个部门”，排除虚拟根及失效部门；完整范围解析中显示正在计算，不能用已加载节点数冒充准确计数。只有计数确定且非零时允许进入批量设置。勾选不直接修改门店属性，属性不按父子关系自行继承。
- **组织页批量直接保存**：扩展组织页批量入口，支持企业实际选中的全部有效部门，超过原 500 部门也可整批处理。界面使用中文结构化字段编辑，不提供 JSON 配置入口；取消影响预览、受影响员工数展示及预览后二次确认，点击保存直接提交草稿。提交中防止重复触发，成功反馈实际保存结果。
- **其他入口边界**：共享门店编辑能力按调用用途明确区分。组织页单部门编辑、门店管理页单条编辑以及 Agent/MCP 的预览/确认协议保持各自既有约定；组织页批量总量扩展不等于放宽其他入口或列表每页上限。
- **服务端写入契约**：直接保存不依赖已调用预览接口。服务端独立核实管理员权限、CSRF、实际目标有效性、字段和门店编码约束；范围解析、校验与写入须对应同一世代/版本。所有目标变更、审计、人员门店投影在同一事务中完成，任一失败整体回滚；内部 SQL 分块不得变成多个独立提交。
- **一致性与冲突恢复**：树、搜索、人员读取、游标、范围解析、计数与批量提交共同绑定 `dataset_epoch` 和 `data_version`，避免初始化后数字版本相同被误认为同一数据集。冲突后保留草稿，刷新并重新核对目标和计数，提示用户再次保存；不自动重放写入，不把新版本新增部门静默并入旧批次。游标须绑定完整查询条件，保留既有限次重读及手动重试行为。
- **数据库交付**：实施前核实目标环境实际 MySQL 版本、结构和连接会话。统一 ORM、迁移与建表入口，遵循 InnoDB、`utf8mb4`、项目排序规则及稳定 ID 的二进制比较约束，每个新增字段提供准确中文注释；仅变更本功能所需结构。提供前置检查、后置验证、备份与失败恢复说明，迁移脚本不构成数据库执行授权。
- **搜索性能**：名称和姓名任意片段是本页明确要求，使用 MySQL 原生能力，按实际规模检查执行计划和延迟；不擅自增加搜索服务，也不把本页要求扩展为其他页面的默认查询规范。具体索引与响应字段命名由实际查询验证决定，不将草案当成已验证契约。

## Testing Decisions

- **测试边界已获用户确认**：主边界复用组织页的用户操作与 HTTP 请求边界，以现有 Vitest、Testing Library 方式验证交互、请求范围、加载批次、响应竞争和草稿恢复。必须证明数据库行为的少量场景复用现有管理 HTTP 契约、持久化及隔离 MySQL 集成边界；真实浏览器在本地容器上串联核心流程。不为 Tree 内部结构、组件私有状态或每个辅助函数新增独立测试入口。
- **好测试的标准**：从用户可见结果、请求/响应契约及最终持久化事实判断成功。相同需求用实现重构后仍成立的断言表达，不绑定 Tree DOM 私有类名、内部函数调用顺序、SQL 拼接文本或组件拆分方式。测试中的 HTTP 合成响应、隔离数据库数据及真实飞书证据分别标识。
- **前端既有先例**：现有组织页行为测试已经覆盖深层搜索保留祖先、父子资源版本冲突、有限重试及批量草稿恢复；共享门店编辑测试已经覆盖规范化提交及冲突保留草稿。扩展这些边界，组织页批量用直接保存断言替换预览断言，并对其他入口保留预览约定进行回归。
- **后端既有先例**：复用管理 HTTP 权限与响应契约测试、查询游标绑定条件/世代/版本测试、同步规范化与原子发布测试、门店校验测试，以及真实 MySQL 下投影与数据版本同事务发布、跨页版本冲突和恢复后世代隔离的集成先例。
- **树与搜索验收**：初次只显示根及一级部门且不读全企业人员；展开只请求直接下级；失败保留内容可重试；完整搜索命中未加载深层部门并返回祖先；清空后恢复原展开；默认有效、可查失效且失效不入批次；搜索中拖拽不可用，局部列表不能覆盖整组顺序。
- **四步选择验收**：覆盖完整循环、所有层级未加载及隐藏下级、不同分支互不干扰、部分下级保留及下一次只取消父部门、清空最后一个下级后的自然状态、根全选/部分时清空、叶节点切换。计数以完整去重有效部门集合为准，计算未完成与零选择均不能开始批量编辑。
- **人员验收**：用至少跨三批的数据验证每批 20 人、无更多停止、失败重试无重复；覆盖快速切部门/关键词/筛选后的迟到响应、滚动与游标重置、直属包含兼职、全部成员跨层去重、总人数随所有条件变化。姓名片段可命中，手机号和 USER_ID 仅精确命中，工号不作为本次搜索字段；账号组合、明确 false、缺省/不可读未知分别验证，历史无效关系不得混入。
- **批量与权限验收**：用超过 500 个有效部门且包含未加载目标的夹具验证准确计数与一次整批保存；确认组织页批量没有预览请求或二次确认，提交中不重复触发。未授权、CSRF 不通过、失效部门、虚拟根、字段错误、门店编码冲突均由服务端拒绝。选择目标不造成写入，成功后显示实际结果。
- **事务与版本验收**：真实 MySQL 验证任一目标校验或写入、审计、投影阶段失败时全批回滚，数据版本不产生部分成功。覆盖计数后发生同步、批量保存发生 409、初始化后相同数字版本但不同世代；草稿保留，目标重核，新增部门不被自动加入，必须用户再次保存。并发排序不得静默覆盖。
- **排序与采集验收**：真实 MySQL 验证刷新及不同管理员读取同一顺序，普通同步不覆盖、新增/移入追加、同 ID 同父级恢复保序和既有初始稳定顺序。使用既有飞书采集边界的合成响应验证手机号及五项账号标志贯穿读取链路，合法空值与缺失、不可读不同；再独立取得实际应用身份的字段读取证据，不能用 SDK 类型替代。
- **工程与环境检查**：后续实现运行相关 pytest、Vitest、前端类型检查、生产构建、受影响的 Ant Design 检查及版本校验。分别核实实际 MySQL 结构/会话、片段搜索执行计划与延迟、飞书字段能力及本地 Docker 浏览器行为；单元测试、离线 SQL、应用健康检查均不替代对应验收。本轮只整理规格，不把计划中的测试报告为已执行。
