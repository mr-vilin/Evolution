## 第一轮答复与确定的规则

### Q1：顺序保存到数据库字段

用户答复：“数据库表形成一个字段，保存到字段里。”

确定采用数据库字段持久化排序。候选实施方案为部门表增加本地 `sort_order` 非负整数字段，表示同一父节点内的展示顺序；不在一个JSON字段中保存整棵树。与原建议一致，拖拽只调整同父级部门顺序，不改变部门隶属、不回写飞书，对管理员共享；这些完整边界会在最终基线一起复核。

建议的顺序维护规则：普通同步保留本地顺序；新增部门及从其他父部门移入的部门追加到新组末尾；同ID、同父级的部门恢复时保留原顺序；未设过顺序的既有部门以ID确定稳定初始顺序。初始化清理重来仍沿用现有业务数据清理边界。多人修改通过版本校验避免静默覆盖。

该段是数据设计候选，不是已创建字段、已执行迁移或已验证实际数据库的结论。

### Q2 与 Q10：搜索字段和匹配方式

用户Q2答复：“部门仅支持名称，人员支持姓名、手机号和用户USER_ID。”

用户Q10答复：“名称和姓名任意片段，手机号和USER_ID精确。”

确定：部门仅搜索名称任意片段；人员搜索姓名任意片段、完整手机号或精确USER_ID。人员搜索限定当前部门及所选成员范围，并与账号状态条件叠加；部门搜索覆盖完整已同步部门，结果保留祖先路径。浏览器尚未加载的数据仍须命中。

手机号读取链路必须补齐，不能将不可读、未采集、未填写统一认定为空。未知值应明确呈现；真实手机号读取权限仍须在实施时核实。手机号格式归一化方式纳入最终实现说明，精确匹配不扩展成后四位或任意片段匹配。

数据库技能的通用规范默认禁止页面全模糊搜索；本需求由用户明确选择名称/姓名任意片段，作为本页限定的产品要求记录。实现应在MySQL原生能力范围内设计查询与索引，按实际数据量检查执行计划和延迟，不擅自增加搜索服务，不把这一要求扩展成其他页面的默认SQL规则。

### Q3：真实账号状态

用户答复：“采用。”

采用真实飞书账号状态标志，保留现有“有效/失效”的生命周期含义。五项原始标志为暂停、离职、激活、主动退出、未加入；未知/不可读值不推断为false。状态可能组合存在，不能未经约定合成互斥枚举。Q8已确认仅查询当前有效部门归属人员；离职/退出历史名单另行设计。

最终实施基线中的筛选候选为单选下拉：“全部”（默认）、“已激活”、“未激活”、“已暂停”、“未加入”、“状态未知”。激活按原始标志true/false匹配，暂停及未加入按各自标志true匹配；本页使用的账号标志有缺省或不可读值时属于信息未完整确认，明确标未知。多个标志可能并存，同一人员可满足多个不同选项，界面展示原始事实，不强行规定互斥优先级。该选项细化是最终基线候选，不伪称SDK原生枚举。

### Q4：成员范围与人数

用户答复：“采用。”

默认“仅展示部门直属成员”。任一当前有效部门归属都算直属，包含兼职，不限于主部门。“展示全部成员”包括当前部门及所有层级的下级部门，同一个人只计一次。“总人数”为当前范围、关键词与筛选条件下的去重匹配总数，与已加载人数分开。

### Q5：父部门四步点击循环

用户明确的顺序：

```text
父部门和下级均为空
  → 仅选父部门，不选子部门
  → 选父部门及所有层级的下级部门
  → 取消父部门，保留下级部门选中
  → 清空父部门及下级部门
```

“所有下级”包含未展开、未加载、被搜索隐藏的下级部门，不能只操作当前浏览器缓存；Q11进一步限定批量选择仅包含有效部门。操作一个分支不改变其他分支的实际选择。点选标题查看人员与范围勾选分别处理。

建议以明确中文范围标记区分“未选”“仅本部门”“本部门及下级”“仅下级”，并补充下级是否全部选中；原生Tree勾选外观不能单独区分四种范围。

### Q6：部分下级的选择保留

用户答复：“采用，保留实际选择并标注部分下级。”

手动调整下级后，允许父部门与部分下级同时选中，保留实际勾选范围，在“本部门及下级”阶段显示“部分下级”。下次点击父部门仅取消父部门、保留已选下级；再次点击才清空该分支。不会自动补选被取消的下级，也不会为保持全选外观而取消父部门。

由实际选择推导范围：父未选且无下级为“未选”；父选且无下级为“仅本部门”；父选且有下级为“本部门及下级”；父未选且有下级为“仅下级”。下级完整性单独标注“全部/部分”。手动取消最后一个下级时，范围自然退回“仅本部门”或“未选”。

该规则记录于 [ADR 0005](../adr/0005-department-selection-cycle.md)。

## 第二轮答复

Q6至Q11均已有答复；Q9采用了数量扩展，并明确取消预览。业务取舍没有未答复项，最后只复核下方完整实施基线。

### Q7：【组织】和叶节点

用户答复：“采用根节点和叶节点的特殊规则。”

确定【组织】的勾选仅用于全选/清空其下所有可批量操作的有效部门，自身不进入门店批量设置；没有下级的叶节点只在选中/清空之间切换，普通父部门采用已确定的四步循环。根节点下已有部分选择时显示实际范围，点击清空；不因根节点自身不可设置而漏掉其下的有效部门。

### Q8：历史离职/退出人员

用户答复：“采用，本轮只查当前成员。”

确定本轮部门人员页只查询具有当前有效部门归属的人员；历史离职/退出人员按历史部门查询另行设计。“展示全部成员”和“账号状态：全部”均不扩大为历史人员查询。切换查看失效部门时也不自动回溯失效关系或推断离职前部门。

### Q9：批量超过500个部门

用户答复：“采用，应该不用预览了，只告诉选中多少个部门即可。”

确定扩展现有500部门批量上限，支持实际选中的全部有效部门；界面显示准确的‘已选N个部门’，去重且覆盖尚未加载的下级，不包含虚拟根与失效部门。取消组织页批量入口的影响预览步骤，编辑后点击保存直接提交；不再额外展示受影响人数或要求通过预览确认才能保存。

保留服务端完整校验、世代/版本一致性、审计与整批成功/整体回滚，不自动执行任何业务写入。历史‘先预览影响，再确认’的组织页批量交互在本轮被此项明确修订。其他独立入口的既有约定不因共享组件被连带移除。

### Q11：失效部门的查询与选择

用户答复：“采用，有效部门默认显示，失效部门可单独查看。”

确定树默认只显示有效部门，提供“显示失效部门”查询开关；失效部门明确标记，仅供查询，不纳入一键全选和门店批量设置。搜索遵循当前部门有效性筛选，查询开关与已展开数据分别处理，不能因某部门尚未加载而漏掉符合条件的结果。

## 日常交互与验收方案

以下细化方案纳入最终实施基线复核，尚不是已完成验收：

- 首次进入显示【组织】及一级部门，人员区提示选择具体部门；一级部门保持收起，按需请求下一层。
- 部门展开加载失败保留节点及已有数据，可重试；已完成加载的节点可复用当前版本缓存。
- 搜索结果保留命中部门的祖先路径，清空后恢复搜索前的展开状态；搜索条件变化不悄悄清空已有批量选择。
- 部门或人员条件变化时清空旧人员页、重置滚动和游标，重新请求20人；过期响应不得拼接到新条件下。
- 向下滚动人员列表续载，显示加载中、失败重试及没有更多；没有下一游标时停止请求。
- 自动解析完整已选范围并展示准确部门数，保留结构化草稿；编辑后保存直接提交，不安排独立影响预览步骤，不因异步树加载漏掉下级。
- 数据版本变化后保留草稿，重新核对实际目标和计数并提示再次保存，不将新版本新增的部门静默纳入旧批量提交。
- 拖拽只允许同父级间隙排序；搜索中的局部结果不作为完整同组顺序写入，候选方案为搜索期间停用拖拽。

## 最终实施基线（Q12待确认共同理解）

Q1至Q11的业务取舍均已有用户答复。以下将已确认规则与必要的工程细化合成可实施方案；Q12只确认整体理解，不再次逐项询问已经作出的选择。

### 树与顺序

1. 使用Ant Design 6.6.4的受控Tree；点选查看人员、展开浏览、范围勾选各自受控。
2. 首次进入显示【组织】及一级部门，一级部门本身收起；右侧提示选择部门，不自动查询全企业人员。每次展开只按需获取该节点直接下级，加载失败可重试。
3. 同父级部门支持拖拽排序，部门表使用本地 `sort_order` 非负整数字段保存顺序；所有管理员共享，普通飞书同步保留。新增/移入新父部门时追加组末，同ID同父级恢复保留原序；初始未排序对象按ID保持稳定顺序。
4. 拖拽不变更部门隶属，也不写回飞书；搜索结果为局部视图，搜索期间停用拖拽，避免用不完整同组结果覆盖顺序。
5. 默认仅显示有效部门，提供“显示失效部门”查询开关；失效部门有明确状态标识，仅供查询，不参加批量设置。

### 搜索与人员

1. 部门搜索只匹配名称任意片段，后端检索完整已同步数据中符合有效性条件的部门，返回命中节点及祖先路径。清空搜索恢复搜索前的展开状态。
2. 人员在一个搜索入口中按姓名片段、手机号精确值、USER_ID精确值匹配，范围是当前部门及所选成员范围；同时叠加账号状态条件。手机号不做后几位匹配，完整号码去首尾空白后比对，不自动猜测国家区号。
3. 只查询当前有效部门归属的成员。默认直属，兼职有效归属也算；“全部成员”包含本部门和全部层级下级，人员去重；历史离职/退出名单另行设计。
4. 部门人员首批20人，向下滚动人员列表再加载20人，停止使用前端全量读取后分页。更换部门或条件时重置游标和滚动，旧请求结果不混入新列表。
5. “总人数”是当前范围和所有条件下的去重匹配总数；与已经加载多少人分开显示。没有更多、正在加载和加载失败均有可理解的反馈。
6. 账号状态下拉单选，默认“全部”，选项为已激活、未激活、已暂停、未加入、状态未知。各项按真实飞书标志匹配，允许同一人员具有多个状态事实；不可读/未采集值明确为未知，保留原有记录有效/失效语义。
7. 补齐手机号和账号标志的采集、存储、读取及字段可读性说明。手机号未知时不将其解释为已证明为空或确定无权限；复用项目既有逐字段检查机制，真实读取能力按实施时证据确认。

### 四步范围选择

1. 普通父部门的点击循环为“均未选 → 仅本部门 → 本部门及全部下级 → 仅下级 → 均未选”。全部下级覆盖未展开、未加载及被搜索隐藏的有效部门。
2. 手动调整下级后保留实际选择；父部门与部分下级同时选中时标注“部分下级”。下一次点击父部门只取消父部门，再点清空该分支。
3. 范围标记明确区分未选、仅本部门、本部门及下级、仅下级；下级是否完整另标全部/部分。一个分支的操作不清空无关分支。
4. 【组织】只全选/清空其下全部有效部门，自身不入批次；部分选中时点击清空。没有下级的叶节点仅选中/清空。
5. 勾选只确定批量操作对象，不直接更改门店属性。最终写入由用户编辑后点击保存触发；门店属性不因组织父子关系自行继承。

### 批量数量与直接保存

1. 扩展组织页批量能力，支持当前企业实际选中的全部有效部门，超过原500部门也可处理；列表接口每页上限与批量总量分别管理，不借此扩展其他入口的限制。
2. 常驻显示“已选 N 个部门”，N为完整范围去重后的有效部门数，不包括虚拟根和失效部门。解析未加载范围期间显示正在计算，不用浏览器当前节点数冒充准确计数；计数确定且存在选中项后才允许开始批量设置。
3. 组织页“批量设置”入口取消影响预览、受影响员工数展示和预览后的二次确认；保留结构化编辑，点击“保存”直接提交当前草稿。零选择时禁用批量入口，提交中防止重复触发，成功后反馈实际保存结果。
4. 本轮修订针对组织页批量入口。共享编辑组件的组织页单部门编辑、门店管理页单条编辑，以及Agent/MCP的预览/确认协议按各自既有范围处理，不能因复用组件而一并移除。
5. 服务端仍独立核实权限、CSRF、实际目标、字段校验和门店编码约束，校验与全部写入、审计、投影更新在同一事务中完成；任何失败整体回滚，不把内部SQL分块误作多个独立提交。
6. 范围计数和提交绑定数据集世代与数据版本，避免初始化后数字版本重复。冲突后保留草稿，刷新可核实的目标与计数，提示再次保存；不自动重放旧写入，不悄悄将新部门并入旧范围。

### 实现模块与验证

- 前端：组织页受控树与范围选择、后台搜索、人员滚动读取、筛选和数量展示；组织页批量入口直接保存；共享编辑入口按用途明确配置。
- 后端：子节点存在标识、查询与统计、四步选择范围解析/计数、超过500部门的批量提交及世代/版本一致性；保留管理员门禁、输入校验与原子性。
- 持久化：部门本地顺序、员工手机号与真实账号状态，统一ORM、迁移与建表入口；不更换数据库、框架或部署拓扑。
- 行为回归：未加载命中搜索、所有层级选择与排除、部分下级保留、根/叶特殊规则、真实去重数量、条件切换后的20人续载、账号未知值与真实筛选、取消预览后的直接保存、409草稿恢复、超过500部门及整批回滚。
- 工程检查：相关pytest和Vitest回归、前端类型与生产构建、受影响Ant Design检查，以及 `node scripts/versioning.mjs check`。对真实MySQL执行计划、结构及会话设置、真实飞书字段能力和本地容器浏览器行为分别取证，不能用单元测试或健康检查代替。
- 交付：Q12确认后实施代码并准备可审查的迁移和恢复说明；数据库执行仍按实际目标及已有授权处理。代码与必要环境检查通过后，依项目标准工具发布本地Docker并验收；不推定远端发布或业务同步授权。
