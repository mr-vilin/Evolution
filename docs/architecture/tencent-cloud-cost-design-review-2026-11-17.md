## 3. 无需让用户判断代码事实的工程修订

以下是已纳入模型的工程处理方式，尚未实现；不新增用户没有要求的财务业务。

1. **执行尝试与配置快照。** 一条 `tencent_sync_job` 表示一次逻辑工作，重试增加尝试记录；实际输入先可靠保存再执行，逐次完整保存处理器真实返回。配置增加并发修订号，逻辑任务冻结账号、业务、期间、口径、处理器契约和必要策略。当前开关、撤权及凭据轮换仍在执行时校验，不能用快照冻结过期授权。
2. **期间提交与批次成功。** 每个日/月期间作为独立提交子任务，父批次只汇总，不领取租约或伪造处理器调用。配置租约由实际子任务持有，覆盖同一逻辑任务的重试等待。连续覆盖不跨缺口，近期实际覆盖独立呈现，不把一个期间成功标为整批成功。整月替换日数据时，删除、写入、回执、尝试结果及进度同事务提交。
3. **重试和恢复策略。** 只对明确可安全重复的限流、网络暂时故障及账单未准备等原因退避重试；权限、账号不符及参数错误不能盲目重试。配置须有尝试预算、轮次截止、租约/心跳、有界排队和补跑限制。停机后合并补齐缺失期间，固定范围及稳定去重身份，不逐个重放已经成功覆盖的所有旧计划点。租约失效后先核对原提交，旧执行者不能覆盖新结果。
4. **金额和产品维度。** 成本保留上游精度，`DECIMAL(24,8)` 仍需真实样本验证。余额 Float 字段须从原始 JSON 解析边界保留十进制数值，不能先经 float 再声称恢复原精度。`Dimensions=business` 对应字典 BusinessCode，模型已使用 `business_code`，避免与子产品 ProductCode 混淆。产品同名不能证明跨期间身份相同。
5. **凭据与云账号绑定。** 后端只解析受控凭据引用，注册/轮换时核实账号，余额每次核对返回 UIN，成本参数与已验证归属一致。CAM 基础只读动作补齐 `finance:DescribeAccountBalance`，成本为 `finance:DescribeCostExplorerSummary`；实际采用辅助对账时再授予对应动作，不要求本期集团权限。[官方费用中心权限表](https://cloud.tencent.com/document/product/598/92835) 已核对，真实授权尚未验证。不在前端、配置 JSON 或日志保存可用密钥。
6. **真实零费用与缺失分开。** 主成本接口没有通用的账单就绪标志；零总计/空产品集不能单凭空页判断。需结合已验证账期、接口契约及必要的辅助对账判断；辅助接口 `Ready=0` 时稍后重试。已过可查历史窗口、权限错误、尚未准备不能以零覆盖旧非零数据。
7. **本次接口契约及审计。** 余额查询、成本查看/导出、账号维护和重拉分别登记动作和权限，复用现有会话与安全校验。私密财务响应采用 `Cache-Control: no-store`；查询审计只保存必要账号、状态、时间、请求关联等白名单摘要，不默认复制余额和整批费用。每次实际入站请求分别计数；内部分页数、逻辑任务数和尝试数分开统计。新增查询或配置不构成全系统审计平台重建范围。
8. **部署与数据库证据。** 设计采用项目 MySQL 8.4 / InnoDB / utf8mb4_general_ci，稳定标识二进制比较；这不是对运行实例的确认。新增表、字段、迁移及 ORM 要有中文注释、兼容类型、显式字符集，迁移交付预检、验证和恢复说明。实现测试通过后按项目规则报告，部署和真实数据库变更继续按当前任务的具体授权执行。
9. **初始化与恢复隔离。** 权威事实为 `dataset_state(id=1).initialization_status == 'complete'`。任务受理时冻结 `dataset_epoch`，每次尝试记录并使用同一值；提交事务锁定状态行，检查 complete、epoch、当前账号/配置及租约。恢复和失败清理重来会改变 epoch，普通完整发布保留已有 epoch，因此无需新增全局代数。旧任务不重新绑定新 epoch；幂等身份包含固定世代，新世代隔离旧活动资格后重新生成补漏任务，不能被旧键阻止入队。组织清理保持现有组织资料边界，不加入云账号、费用或尝试历史；费用期间仍按账号和日期保持当前一份。页面、余额查询、人工提交和 worker 使用同一门槛，余额返回前也核验本次 epoch。

该初始化判断来自 [DatasetState](../../backend/app/persistence/models.py)、[发布器](../../backend/app/sync/publisher.py)、[初始化流程](../../backend/app/initialization/service.py) 和 [恢复入口](../../deploy/recovery.py)。已完成系统没有日常重初始化入口，不能因本轮设计虚构该能力；页面处理 `INITIALIZATION_INCOMPLETE` 时刷新门禁，修正当前仅对 401/403 重检会话的缺口。

## 4. 第一轮问题与用户答复

保留原问题与推荐以便追溯，并逐项记录本轮用户的实际答复。六项业务决策均已明确，不重复询问。

### Q1：实时余额的指标、刷新和本期边界

是否本期将成本与实时余额一起落地，余额主卡使用 `RealBalance`（真实可用余额），现金、赠送、冻结、欠费和信用额度分别展示；进入页面或用户点击刷新时查询腾讯云，显示本次查询时间，失败明确提示，旧值不冒充实时结果；不建余额同步任务和余额历史表，云产品仅预留扩展？

推荐：是。实时表示腾讯云本次查询返回的状态，不承诺源端内部毫秒更新，也不把信用额度混成现金。

用户答复：**是，按建议执行。**

### Q2：近期费用自动复核

是否沿用原日/周/月频率，并在日/周任务每次重查当月截至昨日及上月，在月任务每次重查最近两个已到同步日的完整账月，更早账期保留手动重拉？

推荐：是。该范围解决常见迟到及近期调账，不保证更早历史永远自动一致。已有完整月记录按整月重取，不向其中写重叠日金额。

用户答复：**是，自动复核近期历史。**

### Q3：旧账不可获取时的验收

是否回溯所有实际可取的官方历史，明确显示缺失账月，允许近期数据先使用；旧账导入另行评估，不阻塞近期看板？

推荐：是。不能标记为全历史已完成；缺口、最早已核验月份、实际已覆盖区间和当前最近成功时间分开呈现，避免一个连续边界把近期可用数据也显示成没有同步。

用户答复：**是，缺口可见，近期先用。**

### Q4：一期财务访问范围

是否一期仅向现有管理员白名单开放成本、余额和相关操作，普通组织目录查看者无权访问，查看、导出、账号配置和重拉入口分别执行服务端校验？

推荐：是，沿用现有身份体系；若并非所有管理员都应查看财务，改为明确授予财务资格的管理员，再确认其分配及账号范围，不默认扩建全系统权限平台。

用户答复：**是，仅现有管理员。** 不新增额外财务资格分配流程。

### Q5：与组织初始化解耦

是否保留登录身份及安全校验，但腾讯云配置、余额查询和成本任务不要求飞书组织数据先初始化完成？

推荐：是。不得通过移除会话、CSRF 等安全校验实现解耦；只移除该模块不需要的组织就绪前置条件。

用户答复：**否，必须完成组织初始化后开放。** 采用用户选择，保留整个模块的初始化前置条件；原解耦推荐未被采纳。

### Q6：账号与凭据归属

是否本期按每个独立云账号使用各自只读凭据、查询自身费用及余额建模，不先支持集团代付或统一凭据查询成员？

推荐：是。如果实际存在集团代付或共享集团身份，则下一轮必须确定支付者/使用者视角、成员归属和余额查询路径，不能照普通独立账号接口实施。

用户答复：**是，各账号独立凭据和归属。**
